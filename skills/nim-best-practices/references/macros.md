# Templates and macros: what Lisp learned, in Nim terms

The guide's rules for templates and macros come from the Nim manual and from two Lisp sources.
Lisp has had macros that rewrite code for decades, so its failures are well recorded. Nim's
templates and macros fail the same ways.

## Sources

- Paul Graham, *On Lisp* (Prentice Hall, 1993). The author's free digital edition is at
  https://paulgraham.com/onlisptext.html ("On Lisp © mmii pg"). Read: chapter 8 "When to Use
  Macros", chapter 10 "Other Macro Pitfalls" (10.1-10.3). Chapter 9 "Variable Capture" was read
  only by its section titles. Paraphrased, with short quotes.
- Google Common Lisp Style Guide, section "Macros":
  https://google.github.io/styleguide/lispguide.html (read 2026-11-17). The style guides are licensed
  CC-BY 3.0 (the repository's README). Paraphrased, with short quotes.
- The Racket Guide, 16.1.2 "Lexical Scope": https://docs.racket-lang.org/guide/pattern-macros.html
  ("Racket's pattern-based macros automatically maintain lexical scope").
- The Nim manual (`nim-manual.md`): templates, hygiene, the macros chapter's opening.

## When a macro is justified

On Lisp, 8.1: "By default we should use functions: it is inelegant to use a macro where a
function would do." Macros do two things functions cannot: they control the evaluation of their
arguments, and they are expanded into the calling context. Graham lists the uses:

| On Lisp | In Nim |
|---|---|
| transformation (look inside an argument, as `setf` does) | a macro (a template cannot take its argument apart) |
| binding (introduce variables the caller uses) | a template with the name as a parameter, or `{.inject.}` |
| conditional evaluation (`when`) | a template whose argument sits inside `when`/`if` |
| multiple evaluation (`do`) | a template whose body parameter sits inside a loop |
| using the calling environment | do not; pass it as a parameter (see "Capture" below) |
| wrapping a new environment | a template like `withLock(l): body` |
| computation at compile time | `const` and a proc first; a macro when the input is syntax |
| saving function calls | `{.inline.}`, not a template |

He also lists what macros cost: functions are data and macros are not, macro definitions are
harder to read, and expanded code is harder to debug at run time. The Google guide adds:
"Don't write a macro when a (possibly inlined) function would do", and "Don't use regular macros to
improve performance, use inlining." The Nim manual's style note gives the same order: proc,
generic proc, template, macro.

## Capture (hygiene)

Lisp macros are not hygienic by default. A name the expansion binds can shadow the caller's
names, and a free name in the expansion can pick up the caller's binding. The Google guide:
"Macros should generally be hygienic, binding only symbols provided by the caller or generated by
gensym." On Lisp says that using the calling environment is "usually viewed more as a source of
contagion than a source of pleasure", and that when it happens, it usually happens by mistake.

In Nim, templates are hygienic by default, and `genAst` and `quote` give the names they declare
fresh symbols. The Lisp rule therefore becomes: do not switch hygiene off. `{.dirty.}` is
beautifulnim's BN-08. `parseStmt` on a string discards hygiene too (BN-09). A name the caller
must see is a parameter or `{.inject.}`, and it is documented. The Google guide's version:
"Clearly document unhygienic aspects and side-effects of macros."

## Number and order of evaluation

On Lisp, 10.1: "the arguments to a macro are forms, not values". A form placed twice in the
expansion runs twice. Graham's example is a loop that never ends because its `stop` form has a side
effect and is re-evaluated on every pass. Unless a macro is clearly meant for iteration, it should
evaluate each expression as many times as it appears in the call. 10.2: evaluate them in the same
order they appear. The Google guide: "Only evaluate parameters to a macro once", with
`once-only` as the tool.

A Nim template is the same, typed parameters included: it pastes the argument's tree at each use.
The fix is Lisp's `once-only` written by hand, `let v = x`, in parameter order. A `let` in a
template is hygienic, so no gensym is needed. beautifulnim reports a template parameter used more
than once (BN-10). It counts the widest branch of `if`/`case`/`when` rather than the sum. It ignores
uses inside `typeof`, `compiles`, `astToStr` and `runnableExamples`, and names that the template
itself declares.

## Keep the expansion small

The Google guide: "Macro forms should only process syntax", and "Minimize macroexpanded code,
delegating logic to an implementation function where appropriate (call-with style)". Expanding a
body more than once makes the expansion harder to read and the binary larger. In Nim, the macro
checks and rearranges syntax, and the expansion calls an ordinary proc that holds the logic and has
its own tests.

## Not carried over

- Reader macros: Nim has none. Its macros cannot change Nim's syntax (the manual).
- Compiler macros: in Nim, use `{.inline.}` procs. The guide does not recommend term-rewriting
  macros.
- The Google guide's advice to give a body macro an empty parameter list for later growth applies
  to Lisp's syntax. It has not been checked for Nim, so the guide says nothing about it.
